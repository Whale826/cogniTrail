知迹（CogniTrail）

AI 协作开发中的理解保持与决策留痕系统 —— GitHub 竞品调研结果 · 二次开发策略 · 技术路线

文档类型　调研 + 实施方案 数据快照　2026-10-12 调研方法　GitHub Search API · 16 组关键词

本文件回答四个问题：这个产品做什么、GitHub 上已经有什么（调研结果）、为什么我选择站在前人肩膀上做二次开发、我自己的增量是什么、靠哪些技术实现。

一句话交代：知迹是一个挂在 AI 编码 Agent 旁边工作的「协作理解层」——不替用户写代码，也不教用户写代码，而是在 AI 完成开发之后，把关键决策整理成可回答的卡片，写进用户自己的仓库，并在几天后抽查用户是否真的还记得。
调研结论是：相关赛道已经很拥挤，但所有现存方案都挤在"过程内"，没有一个正面服务"事后"；且其中唯一无人实现过的机制是"延迟理解探针"——这将成为本项目的核心独特性，而其余部分通过复用成熟开源件完成。

一这个产品做什么

先明确目标，后面的调研与方案才有落点。

1.1 要解决的问题

AI 已经能完成大部分编码工作，但它的完成速度已经超过了理解速度。结果是任务交付了，开发者却没有形成足以判断、维护和接管这项工作的理解。这不是"不肯学习"——查语法、写样板代码本就该交给 AI。问题在于有四种能力必须留在人身上，而当前的交互方式正在把它们一并卸载掉：知道项目的目标与约束、知道修改会影响哪里、理解方案之间的取舍、判断结果是否可信并从哪查起。

1.2 定位与判据

目标：让用户借助 AI 完成开发的同时，保持对项目结构、关键决策与变更后果的理解与控制。
可观察判据：用户让 AI 完成一个登录功能后，应当能回答——身份信息存在哪里、权限在哪里检查、会话如何失效、哪些地方被改变、出了问题该看什么证据。
至于每一行样板代码都要求理解，既不可能也没有必要。

必须坦率承认的三点：
  • "认知负债（cognitive debt）"这个词已经被至少 7 个公开仓库使用——它不再是一个新颖措辞，而是一个已被命名的品类。继续拿它当卖点会被判定为跟随者。
  • 我原以为最核心、最难的"证据坐标 + 写盘前校验"，explain-pr（MIT）已经实现并开源了。
  • 我原以为最独特的"决策记录落盘 docs/decisions/"，AgDR 标准 + archgate + decision-record-toolkit 三件套已经做完了，而且比我的方案更完整（有标准、有 schema、有 CI 门禁、有作废机制）。

2.3 关键发现：所有人都在解决前半句，没人管后半句

把 30 多个项目按 「服务对象 × 作用时机」 两个维度摆开，空白区会自己显形：

发现：所有人都在解决"用 AI 的时候别变笨"。没有人解决"用完之后，我怎么知道我真的还记得、以及怎么向别人证明我懂"。而知迹最初的用户正好卡在这里——作业是 AI 做的，答辩在三个月后，中间没有人问过任何问题。这不是"防止卸载"的场景，是"事后补理解"的场景。

三为什么选择"站在前人肩膀上"做二次开发

调研的第二个结论是：这个方案的绝大多数零件，都已经有成熟且许可证宽松的开源实现。从零自研既不经济，也会错过答辩时最该讲的那句话——"我知道别人做到了哪一步"。

4.3 差异化的三重根据

既然单项机制大多已被做过，差异化就只能建立在"组合与出口"上，这也是本方案能站得住的三个理由：

7.2 为什么价值会随时间增长

  • 产物是可积累的资产。落盘的是用户仓库里的 Markdown 文件，可以被提交、被审查、被带走，而不是一段会被遗忘的聊天记录。
  • 决策记录与代码版本、验证结果关联后，价值随时间增长——它能回答"为什么当初这么设计"，而聊天记录不能。
  • 它能对抗"功能被大平台吸收"。即使大厂也做解释模式，写进用户自己仓库、属于用户本人的决策档案，是不可被平台收回的。

八诚实的边界与风险

一个负责任的方案必须同时说清"哪里还不确定"。以下不是免责声明，是后续要验证的清单。

8.1 三个必须说明的局限

  1. MIT 的"Your Brain on ChatGPT"目前为预印本，尚未通过同行评审，样本 54 人，任务是写作而非编程。
  2. "AI 让人变慢"不是稳健结论。METR 在 2026 年 2 月发布了方向翻转的后续数据，且 METR 自己声明该结果不可靠（选择偏差）。稳健的结论只是"感知与现实存在系统性偏差"。
  3. 本方案不主张"AI 降低长期认知能力"，只主张"完成任务的当下，理解没有被同步建立"——后者有直接证据，且可测量。

8.2 对照实验不能省的那一组

验证时必须与"现有 Agent + 计划／解释模式"比较，而不是与完全不解释的工具比较。如果只和"裸工具"比，会严重高估本方案的价值。真正的对手是用户已经能免费开启的 Cursor Plan Mode、Claude Code Learning Mode、Kiro 等。
因此对照组必须有三组：① 原有 Agent　② 原有 Agent + 计划／解释模式（真正的对手）　③ 本方案。

8.3 可能被大平台吸收

本方案的每一项单独机制几乎都被人做过，差异仍可能被大厂吸收。能否形成优势，取决于是否在一个具体工作场景（学生答辩 / 陌生项目接手）中明显做得更好，而不是功能数量更多。
