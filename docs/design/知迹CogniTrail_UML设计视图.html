一需求分析

在进入 UML 视图之前，先用一节把"这是什么东西"讲清楚。看过设计方案的人常会问：它是一个独立产品、一套软件，还是一个 agent 插件？下面的定位、形态与判据回答这个问题。

1.1 一句话定位

知迹（CogniTrail）是一个面向开发者的「AI 协作理解层」。它不替你写代码，也不教你写代码，而是在你用 AI Agent 完成开发的过程中，帮你保住对项目结构、关键决策与变更后果的理解与控制。

1.2 产品形态：它是 agent 协作层，不是 agent 本身

知迹不自己生成代码，而是挂在现有的 AI 编码 Agent（Cursor、Claude Code、Copilot 等）旁边工作。它的物理载体是"一个 IDE 侧栏扩展 + 一个 CLI 命令 + 一个本地 Node.js 服务"，最终产物不是聊天记录，而是写进用户自己仓库的 Markdown 文件（docs/decisions/*.md）。据此可以明确回答它"是不是一个产品 / 软件 / agent 插件"：

表 2　产品形态界定：它是什么、不是什么
候选说法判断说明
一个 Agent 插件 / IDE 扩展是（主要形态）挂在现有 Agent 旁运行，自身不接管执行、不产生代码变更
一个开发者工具（CLI + 本地服务）是可由命令行触发，核心逻辑本地运行，结果落进仓库
一个独立的 SaaS 平台 / 网站不是第一版不依赖云端账号，也没有独立登录入口
一个替代 Agent 的执行器不是它不写业务代码，只负责"理解"与"留痕"
一个编程教学平台不是不系统讲课，只在真实任务的关键处提问
一款代码质量 / 安全审计工具不是审查对象是"你对变更的理解"，不是代码本身的对错

1.3 要解决的问题

AI 已经能完成大部分编码工作，但它的完成速度已经超过了理解速度。结果是：任务交付了，开发者却没有形成足以判断、维护和接管这项工作的理解——这是"认知卸载（cognitive offloading）"留下的认知负债。

这不是"不肯学习"的问题。查语法、写样板代码、整理文档，本就应该交给 AI。真正的问题在于，有四种能力必须留在人身上，而当前的交互方式正在把它们一并卸载掉：

  • 知道项目的目标、组成部分和关键约束；
  • 知道当前修改会影响哪里；
  • 理解主要方案之间的取舍；
  • 判断结果是否可信，出问题时知道从哪里查起。

四组独立研究（Anthropic 随机对照试验、MIT "Your Brain on ChatGPT"、METR 现场试验、Stack Overflow 2025 开发者调查）指向同一个结论：问题不出在"AI 做错了"，而出在"AI 做对了，人却没有跟上"。

1.4 产品目标与判据

目标：让用户借助 AI 完成开发的同时，保持对项目结构、关键决策与变更后果的理解与控制。
可观察判据：用户让 AI 完成一个登录功能后，应当能回答——身份信息存在哪里、权限在哪里检查、会话如何失效、哪些地方被改变、出了问题该看什么证据。
但：至于每一行样板代码，都要求用户理解，既不可能也没有必要。

1.5 目标用户与切入场景

首批用户是有编程基础、但对当前项目不熟悉的开发者。更完整的用户分层如下：

表 3　目标用户分层
用户主要痛点产品价值切入优先级
接手陌生项目的开发者不清楚模块关系、约束与历史决策帮助定位、理解与安全修改很适合

切入场景：一位具备编程基础的开发者，进入一个陌生代码库，使用 AI 完成一次真实的功能修改。这个场景同时包含"宏观认识"与"执行过程理解"，效果可以直接观察，后续再延伸到团队交接、代码审查与持续开发。

1.6 明确的非目标与工作时机

为避免范围失控，以下四件事本产品明确不做：

  • 不是编程教学平台；
  • 不是代码质量或安全审计工具；
  • 不是替代现有 Agent 的执行器；
  • 不要求用户阅读全部解释。

产品在两个时机工作，但重心在事后——因为用户最强烈的痛点恰恰出现在"AI 做完了、我却说不清它做了什么"的那一刻：

表 4　两条工作通道
通道时机形态是否打断用户
过程内出现关键决策时侧栏中的决策卡片极少，仅关键节点
事后任务结束后落盘成文件（决策记录、问题卡、证据索引）完全不打断

事后通道之所以是重心，是因为落在用户自己仓库里的文件是可积累的资产，也会随代码版本与验证结果关联而增值——聊天记录则不会。

二用例图

系统边界内是六项用例，边界外是四类参与者。需要注意的是，大模型服务与 Agent 运行时是被系统调用的外部参与者，而不是本系统的组成部分——这决定了"兼容多 Agent"是集成难度而非功能数量。

三类图

类图的作用是把设计方案的词汇固定下来。图中琥珀色的两个类不是普通数据结构，而是设计方案里明写为"不依赖用户主动性"的两道防线：EvidenceRef 强制每条结论指到文件与行号，Probe 用数天后的复测替代点击行为。

读图要点：SemanticStep.status 的取值必须区分四态——计划修改 / 已尝试执行 / 已产生变更 / 已通过验证。设计方案明确反对用一份初始任务清单冒充实时进度，这个约束就落在该枚举上。

四时序图

时序图只画 P0 最小闭环——读 diff、找决策点、生成卡片、校验证据、落盘。它是整个方案里唯一被要求两周内跑通的部分，也是"这些卡片有没有用"这个问题的可证伪载体。

五活动图

时序图回答"按什么顺序"，活动图回答"什么条件下才允许产出"。两条判定分支是设计方案的硬约束：候选超过 5 张必须按影响排序截断，证据无法定位必须丢弃。

六状态图

把决策卡片单独拿出来做状态图，是因为它有两条通往终态的出口。这两条出口恰好对应两款"看起来很友好、实际上在加深卸载"的失败产品：不加判据地什么都解释，以及不校验证据地写一段通顺的话。

七部署图

部署图交代第一版技术选型的落地位置。设计方案的估算表明，难度集中在"可靠同步"而非生成解释，而同步问题的边界恰好由这张图划出：IDE 扩展、本地服务与 Agent 运行时分处三个执行环境。

由视图反推的三条设计约束：
  • 状态与计划必须分开维护（图 2 中 TaskPlan 与 SemanticStep.status 各自独立）——否则计划重排后会拿初始清单冒充实时进度。
  • 证据校验必须在写盘之前（图 3、图 4 的闸门位置）——放在写盘之后等于允许编造解释流入交付物。
  • 理解指标不能来自界面事件（图 5 中「已复测」由抽样与作答触发）——点击行为正是要防范的对象，不能同时充当成功指标。
