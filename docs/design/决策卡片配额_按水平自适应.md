# 决策卡片配额：从「固定 5 张」到「按人给」

> 状态：设计稿（`src/quota.py` 已按本文实现，41 项测试通过；尚未接入主流程）
> 触发问题：「决策卡片太多了」

---

## 0. 结论先行

1. **「太多」其实是三件事**：单次生成太多、库里越积越多、界面把全部卡片一次铺开。
   三层的解法完全不同。现在的代码只处理了第一层（而且处理错了，见 §5）。
2. **用户水平不是一个变量，是两个**：**专业度**（懂不懂）和**关切度**（这一次在不在乎）。
   数量主要由关切度定，专业度定「该留哪几张」。把两者揉成一个「水平」，
   会推出「专家→越少」的单调曲线，把中间层（正在学的人）的价值压掉。
3. **两端都少，但原因相反**：
   - 工程师：卡片里多数内容他自己能从 diff 读出来 → 只留「代码里读不出来的」；
   - 不懂技术：读一张要 30–60 秒，读不完就整批放弃 → 只留「跟我有关的」；
   - **半懂的人最多**：他每张都能学到东西。
4. **上限由供给决定，不硬凑**：只改了一个常量的一轮，给 5 张必然是 3 张水货。
   `N = min(配额, 真实候选数)`。
5. **可疑痕迹不占配额**：无论用户多外行、配额多小，「原有的校验被删掉了」必须留。
   为了少给几张而裁掉它，是这套系统里最坏的省事。
6. **最紧急的一刀在展示层**：`_fill_cards` 把 74 张卡全铺进横向滚动条。
   生成层再精准，界面一次铺 74 张也还是「太多」。

## 1. 先把「太多」拆成三个问题

| 层 | 现象 | 现在的代码 | 该由谁管 |
|---|---|---|---|
| 单轮 / 单次生成 | 点一次「生成决策」，出来 10 张 | `max_cards=5` 截断 | 配额（本文 §6） |
| 项目库累计 | `docs/decisions/` 里 74 张，还在涨 | 无上限，靠手动「整理决策」 | 策展 + 归档（不在本文） |
| 界面展示 | 一屏铺 74 张，横向滚很久 | `_fill_cards` 全量渲染 | 展示层收敛（§7.1，**先做这个**） |

诊断顺序很重要：**先量一下「多」发生在哪一层**。
`docs/decisions/` 现在有 74 张卡片 —— 如果用户抱怨的是打开面板看到的那一片，
那问题 90% 在第三层，改配额只能治标。

## 2. 行为分析：用户到底怎么用这些卡片

### 2.1 三种回查场景

| 场景 | 用户的问题 | 他要的是 | 对数量的偏好 |
|---|---|---|---|
| **审计** | 「AI 这轮有没有偷偷放水」 | 覆盖：高风险的一个都不能漏 | 少而准，但**不能有假阴性** |
| **定位** | 「上次那个阈值是为啥定的」 | 精确命中一条 | 越少越好，多了是干扰 |
| **汇报** | 「跟老板/客户讲清这周干了什么」 | 叙事：谁先谁后、为什么改 | 5–7 条封顶，多了讲不完 |

三种场景的共同点：**没人是为了「读完所有卡片」打开这个面板的。**
卡片是索引，不是文档。索引的价值在命中率，不在条目数。

### 2.2 阅读成本（决定上限的硬约束）

| | 扫一张标题 | 展开读一张 |
|---|---|---|
| 工程师 | 1.5–2.5 秒 | 10–20 秒 |
| 不懂技术 | 3–5 秒 | 30–60 秒 |

一次回查的心理预算：**1.5–2 分钟**（超了就关掉，改去问 AI）。

- 纯扫描找东西：120 秒 ÷ 2.5 秒 ≈ 48 张 —— 但注意力在第 10 张后滑坡，
  用户开始靠滚动条位置猜。实际拐点在 **5–7 张**。
- 要读详情：120 秒 ÷ 30 秒 = **4 张**（非工程师）；÷ 15 秒 = **8 张**（工程师）。
  扣掉判断和切换成本，落到 **4 / 6**。

### 2.3 一屏能放几张（物理上限）

卡片宽 196 逻辑像素 + 10 间距。1280 逻辑宽度下 **6 张**。
第 7 张起必须横向滚动，而**滚出去的部分点击率断崖**（用户不知道那里还有东西）。
所以任何配额都不该超过 6，除非用户明确说「我要逐条看」。

### 2.4 边际价值递减

第 1 张卡的信息量（"AI 到底干了什么"）最大；第 5 张开始，用户已经建立了
对这次改动的整体印象，新增卡片的边际信息量接近 0，但**噪声在累加**：
多一张卡就多一次「这条跟我有关吗」的判断，这个判断本身消耗注意力。

> 结论：卡片数量对价值的曲线是**先陡后平再负**。目标不是「尽量多记」，
> 而是停在曲线拐点之前。

## 3. 关键修正：不是「水平」，是「专业度 × 关切度」

用户最初的假设是：**不专业 → 少；专业 → 更少**（单调）。
这个假设对了两端，但会误伤中间，而且没解释「为什么专业也要少」。

拆成两个轴之后，每一格都能单独解释：

|  | **不关切**（只想知道成没成） | **关切**（要弄明白） |
|---|---|---|
| **懂技术** | 2 张：只给「有没有风险」 | 4–6 张：只给代码里读不出来的 |
| **不懂技术** | 1 张（甚至 0 张，给一句话） | 4 张：只给「跟我有什么关系」 |

四个真实用户落进去：

- **老板 / 客户**：不懂 + 关切 → **4 张**，全部讲影响（会不会丢数据、快不快、花多少钱）
- **工程师审自己项目**：懂 + 关切 → **4 张**，全部讲取舍（还考虑过什么、动了哪层保护）
- **初学者 / 跨领域工程师**：半懂 + 高度关切 → **5–7 张**，全字段，因为他每张都在学
- **路过的同事问一句「能用了吗」**：不懂 + 不关切 → **1 张**，或干脆一句话

**这就是为什么「两端都少」成立**：工程师少是因为**冗余**（他读得出来），
外行少是因为**读不动**。原因相反，结论相同 —— 但中间层不能被一起压掉。

### 3.1 三个量，别混

| 量 | 时间尺度 | 决定什么 | 存哪 |
|---|---|---|---|
| 专业度 `level` | 长期画像（跨会话） | **留哪几张**（筛选权重） | `~/.cognitrail/profile.json` |
| 关切度 `interest` | 当下（按任务/会话） | **给几张**（配额） | 每次现算，不落盘 |
| 供给 `supply` | 本轮 | **最多能给几张**（不硬凑） | 候选数 |

关切度必须按任务算，不能进长期画像：同一个工程师，赶时间时也只看结论；
同一个产品经理，上线前 review 时会逐条追问。

## 4. 目标数量

### 4.1 单次生成的上限

| 档位 | 只想看结论 | 一般 | 要逐条看 |
|---|---|---|---|
| L0 只问结果 | 1 | 1 | 2 |
| L1 不懂技术 | 2 | **4** | 5 |
| L2 懂一点 | 2 | **5** | **7** |
| L3 工程师 | 2 | **4** | **6** |

读法：
- 行内最大的是 L2 —— 中间层最该多给；
- L1 的「要逐条看」只放到 5：不是不给他，是他真的读不完；
- L3 的「要逐条看」放到 6：审计场景他愿意多花一分钟；
- L0 一律 1–2：他要的是结论，不是卡片。

### 4.2 三个层级的建议值（别只调一个）

| 层级 | 建议 | 现在 |
|---|---|---|
| 每轮（一次 AI 回合） | 0–2 张 | 无独立上限，靠整批 5 张兜 |
| 每次生成（点一次按钮） | 上表 | 固定 5 |
| 界面默认展示 | 首屏 4 张 + 「展开」 | **全量 74 张** |

历史卡片**不该在生成层被删** —— 删了就追溯不了。
累计层用「折叠 / 按阶段分组 / 已归档」收敛，可展开。

## 5. 现有实现的两个真问题

### 5.1 截断顺序 ≠ 重要性顺序

`cardgen.generate()`（`src/cardgen.py:203`）与 `cardgen_session.generate_from_session()`
（`src/cardgen_session.py:768`）都是：**边生成边写盘，凑够 `max_cards` 就 `break`**。

意思是现在的「上限 5 张」= **最早碰到的 5 个**，不是**最值钱的 5 个**。
一个文件改得多、或者一轮话说得多，就能把名额全占掉，后面阶段的关键决策一条都进不来。
这比「数量多」更严重：**该留的没留下**。

### 5.2 没有供给约束

`max_cards` 是「最多 5」，但代码里没有「不足 5 就不补」的表达 —— 提示词还在
要求模型「找出所有决策点」。只改一个常量的一轮，模型会硬凑出几条来交差，
这正是「凑数卡片」的来源。`quota` 的 `min(配额, 供给)` 就是为这条写的。

### 5.3 累计没有展示层收敛（最影响体感）

`gui.py:1753` 的 `for index, card in enumerate(cards)` 把库里所有卡片
一张一张 pack 进横向滚动条。74 张 = 用户要横向拖 12 屏。
即使生成层完美，这一层不改，体感永远是「卡片太多」。

## 6. 算法

实现在 `src/quota.py`（纯函数，不调模型、不读文件、不依赖 Tk）。测试在 `tests/test_quota.py`。

### 6.1 信号：只认三类硬东西

| 类别 | 例子 | 权重 | 为什么可信 |
|---|---|---|---|
| 术语 | 幂等、竞态、校验、绕过、backoff | 每个 +0.45，封顶 1.35 | 踩过坑的人才会顺口说 |
| 坐标 | `config.py:42`、`load_config()`、`COGNITRAIL_TONE`、``` ``` ``` | 每个 +0.28，封顶 0.95 | 能指名定位的人一定看得懂卡片 |
| 约束 | 「不要改 X」「必须兼容」「在不改变 Y 的前提下」 | +0.5 | 这是工程判断，不是许愿 |
| 反向 | 「卡住 / 看不懂 / 有什么用 / 没反应」 | 每个 −0.4，封顶 1.2 | 描述现象，不是问机制 |
| 意图 | 「怎么保证 / 取舍 / 根因」+0.35；「这是什么 / 怎么用」−0.35 | | |
| 只问结果 | 整句 = 「好了吗 / 能跑吗 / 结果呢」 | −1.6 | 关切度最低的形态 |

**刻意不用**「句子越长越专业」：外行描述困惑时话往往更多。
也**不做关键词堆砌**：词按长度从长到短匹配并抹掉，
「反序列化」不会同时算中「序列化」；堆术语但说「看不懂」的会掉回 L1（有哨兵测试）。

分档（不对称，宁可高估）：

```
score ≥ 0.9            → L3
0.25 ≤ score < 0.9     → L2
score ≤ −1.2 且 ≤12 字 → L0
其余                    → L1
```

L0 额外要求「短」：长句抱怨说明他在乎，那是 L1（关切但不懂），
不该被归到「只问结果」里只给 1 张。

### 6.2 画像更新：冷启动 + 迟滞 + 可钉住

```
前 2 次提问：不下判断，用先验（默认 L2，或用户选的档位）
升档：连续 2 次同向证据
降档：连续 3 次同向证据        ← 刻意不对称
单次：最多动一档
用户显式选过档位（pin）：自动判断不再改，但继续记样本
```

为什么降档更难：专家问一句「这啥」很正常（他在问不熟的领域）；
外行偶尔甩出一条提示词模板也正常（那不是他的水平）。
对称的阈值会把这两种情况都判错，而且是往「把人看低」的方向错。

### 6.3 关切度（每次现算）

```
追问细节（哪一行 / 依据 / 取舍）   +2 ~ +4
说明用途（我要给客户解释 / 上线前）  +2
连着追问 ≥3 轮                    +1
点开过详情 / 点过证据坐标           +1 ~ +4（行为信号，需要埋点）
连着关掉 ≥3 张卡                   −3（比任何文本都说明问题）
整句只问结果                        −2

≥4 → high    ≤−2 → low    其余 → mid
```

门槛从 `≥1 → mid` 改成 `≤−2 → low`，是被一次实测逼出来的：
diff 那条链路只有「提交说明」一句话可读，它既不会命中「哪一行」也不会命中
「只想看结论」，得分恒为 0 —— 落到 low 就是每次抽卡都只给 1–2 张。
**没有信号 ≠ 不想看**：low 该由**负信号**触发（问结果、连着关卡片），
而不是由「我们没读到什么」触发。

### 6.4 配额

```
N = min(_CAP[level][interest], supply)
```

没有 `max(..., floor)`：**不补足**。

### 6.5 留哪几张

1. **安全例外**：`audit.signal_is_high()` 为真的卡片（判为存疑，或扫出高危痕迹）
   **不参与竞争、不占配额**，最多额外 3 张，超出部分由界面合成一句「另有 N 条存疑」。
   注意**不是** `card_is_flagged()`（那个还包含「证据不充分」）：
   「原有的校验被拿掉」是代码的事实，跟读者水平无关，必须给；
   「我们没核对上」说的是**核对状态**，不是代码状态 ——
   凡是核对不上的都给免死金牌，等于在审计最弱的时候配额自动失效，
   小白界面又会变回一排卡片。这类卡片照常参与排序，`counts` 里照实记一条。
2. **价值分** = tier 基分（key 6 / normal 3 / minor 0） + 档位修正：
   - L3：有具体 alternatives +2、control 被绕过/删除 +2、why ≥20 字 +1、机械改动 −3.5
   - L1：impact 命中用户可感 +3、有 risk +1、纯内部改动 −3
   - L0：impact 命中用户可感 +4，否则 −4
   - L2：不加权（他要的是「全字段、按重要性排」）
3. **阶段轮转**（不是从头取）：按 stage 分桶，每轮每桶取 1 张。
   保证「这次最重要的 5 个决定」，而不是「最早碰到的 5 个」。
4. **同文件上限 2 张**（key 放宽到 3），防止一个热文件刷满整条。
5. **排序键全字段**（value, stage, file, lines, decision）：
   同一批候选不管什么顺序进来，选出来的是同一批（有 6 次打乱的测试）。

### 6.6 一句话解释

每次都给一句可展示的话，让用户知道**为什么只有这几张**：

> 按 工程师 · 一般 给 4 张（候选 9 张，其中存疑 1 张不占名额），另有 4 张按价值排后未列

藏在设置里的规则等于没做。用户看不懂配额，就会以为功能坏了。

## 7. 接入点（按优先级）

### 7.1 展示层先做（改动最小、见效最快）

- `gui._fill_cards`（`src/gui.py:1730`）：默认只渲染最近 `N` 张（N 取配额表 MID 列），
  末尾加一张「还有 80 张 · 展开」。展开后**按 stage 分组**，不要还原成一条长龙。
- `dashboard.load_cards`（`src/dashboard.py:129`）：HTML 同理，默认 20 张 + 按阶段折叠。
- 这样即使生成层一张都不改，体感也会立刻从「74 张」变成「4 张 + 一个入口」。

### 7.2 生成层（已落地）

`cardgen_session.generate_from_session` 与 `cardgen.generate` 都改成了两段式：

```
现在：for 窗口 → 抽 → audit → 收进 candidates（不写盘）
      → quota.select(candidates, level, interest) → 只写留下的那几张
```

要注意的三点：
- `index_offset` 在写盘时才用，延后不影响增量；
- `audit.opinion()` 的 `counts` 要按**全部候选**算，不能按写盘数算 ——
  否则「未列」的那几张会从审计意见里消失，等于**用配额把审计意见洗白了**。
  `write_summary()` 也照这个来：它多收一个 `candidates=` 参数专供算意见，
  表格仍然只列写盘的那几张，并在头部写明「候选 N 个，其中 M 个按配额未展示」。
- 候选要有**自己的上限**（`max(16, max_cards * 4)`）：原来 `凑够 max_cards 就 break`
  同时也是「别再调模型了」的刹车，收全候选后这个刹车没了，
  不改就会对着一整份 diff 一路抽下去。

### 7.3 配置与界面

- `config.py:195`：`COGNITRAIL_MAX_CARDS` 保留（兜底硬顶），新增
  `COGNITRAIL_LEVEL = auto | L0 | L1 | L2 | L3`，默认 `auto`。
- 界面：顶栏「写法」按钮旁加一个「卡片量：自动（工程师·一般）」的小字，
  点开可钉住档位 —— 与 `0.12.0` 的写法弹出层同一套交互（一眼可见，别塞进设置页）。

### 7.4 埋点（决定这套算法有没有用）

`probe.db` 记 4 个事件：卡片展示 / 详情打开 / 证据坐标点击 / 卡片被关掉。
没有这个，关切度只能靠文本猜，而文本是最弱的一路信号。

写盘数 ≤ 配额、`counts` 按候选算、汇总表里不出现被裁掉的卡片。

有两个坑值得记：
- **`max_cards` 仍然是硬顶**，且比配额优先保留「有发现」的卡片。
  配额是「按人给几张」，`COGNITRAIL_MAX_CARDS` 是「绝不给你超过这么多」，
  两者冲突时以「别漏掉可疑的」为准。
- **`samples/demo-repo` 必须每次重建 `.git`**。原来是在旧历史后面追两笔提交，
  一旦上一次 build 被打断，两次提交都成了空提交，`HEAD~1..HEAD` 变成空 diff，
  抽卡器只会说「没有检测到改动」—— 而测试报的是「返回结构不对」，
  查了半天才发现夹具坏了。现在 `build(dest=...)` 可以指定目录，
  每个用例一个独立仓库。

## 8. 验收

### 8.1 离线（已通过）

`python tests/test_quota.py` → **42 项检查全过**。其中五条是哨兵，别删：

1. 两端少、中间最多（防单调化回退）
2. 堆术语 + 「看不懂」不许判专家
3. 冷启动两次不动、降档要三次、一次只动一档
4. 有发现的卡片不占配额且不被裁（**只认 `signal_is_high`**，不认「证据不充分」）
5. 打乱顺序结果不变（防「按文件顺序取前 N」复活）

`python tests/test_quota_flow.py` → **24 项**，测「接进生成流程之后」：
写盘数 ≤ 配额、`max_cards` 仍是最硬的闸、试运行摆全部候选、
`counts` 按全部候选算、汇总表里不出现被裁掉的卡片。

### 8.2 线上（改完接入后看）

| 指标 | 目标 | 说明 |
|---|---|---|
| 卡片打开率 | > 30% | 展示的卡里有多少被点开。低于 20% 说明配额还是太多 |
| 单卡停留中位数 | > 3 秒 | 低于 2 秒说明在扫，不是在读 |
| 「展开全部」点击率 | < 15% | 高说明默认配额太小；低说明折叠做对了 |
| 手动整理/删卡次数 | < 10% 会话 | 高说明生成质量差，不是数量问题 |

指标比测试重要：**配额调得对不对，只有打开率能回答**。

## 9. 这套会错的地方

| 情况 | 会怎么错 | 兜底 |
|---|---|---|
| 专家问一个完全陌生的领域（「这个 CSS 怎么居中」） | 被打低，配额变小 | 降档要 3 次；且他只丢了 1–2 张 |
| 外行复制了一段技术提示词 | 被打高，配额变大 | 升档要 2 次；且「看不懂」这类词会拉回来 |
| 用户全程只打字问、从不点卡片 | 关切度长期 low，卡越给越少 | 给个「多看几张」的显式开关；别让算法自己把门关死 |
| 项目本来就只有一个决策点 | 配额 5 但只给 1 | 这是对的，不要为了「看起来充实」补到 5 |
| 卡片质量差（凑数、重复） | 算法只能排序，不能创造价值 | 这是 `curate` / 提示词的活，不要指望配额解决 |

最后一条要说清：**配额只能解决「数量」，解决不了「水」。**
如果卡片本身废话多，把 20 张减到 4 张，只是把废话变少，不会变成金子。

## 10. 不做的事

- **不让模型判断用户水平**：模型会迎合（觉得用户专业就写得深，然后越写越深）。
  判断放在脚本里，模型只看得到「写几张、写多细」的结果，看不到理由。
- **不把推断出的水平写进卡片正文**：那是猜测，不是事实。
  它只影响「给几张、留哪张」，卡片里一个字都不该出现「用户是外行」。
- **不用 AI 回复的长度/难度当信号**：那是我们自己控制的东西，会形成反馈回路。
- **不在生成层删历史卡片**：少给是「这次不展示」，不是「删掉」。
  追溯不了的记录不叫记录。
