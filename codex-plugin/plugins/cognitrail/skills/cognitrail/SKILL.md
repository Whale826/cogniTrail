# 知迹 CogniTrail

一句话：**知迹不总结代码，它记录「决定了什么」。**

一份 diff 的普通总结会说「修改了阈值、加了重试」。知迹要产出的是另一种东西：
`config.py:5` 这行把验证集比例定成 0.2 —— 为什么是 0.2，不是 0.1 或 0.25，放弃了什么，代价是什么。

## 四条不可违背的规则

**1. 每张卡片必须钉住真实坐标。** 卡片的 `file` 与 `lines` 必须指向目标仓库里真实存在的文件和行号，
并且必须用闸门脚本实测过一遍。写完不校验的卡片等于没写。

**2. 定位不到就丢弃。** 闸门不通过的卡片，不写盘、不展示、不汇报成成果。
宁可只交 2 张真的，也不要在 5 张里混 3 张看起来很像但指不到东西的。

**3. 只记决策点。** 纯格式化、改名、加注释、删空行、升级依赖版本号 —— 不算。
判据只有一句：**换一个同样合理的选择，结果会不会不同？** 会不同，才是决策点。

**4. 你是审计师，不是记录员。** 写代码的是 AI，它在会话里说的「我为什么这么改」
是**被审计方的口述**，不能当成结论抄进卡片。所以每张卡片必须多给一条
`claim`：**能被回文件核对的事实断言**（例：`阈值由 0.5 改成 0.35`）。
审计脚本会拿里面的数字与标识符，去 `file:lines` 那个坐标附近找一遍：
一个都找不到、或只对上一半，这张卡就会被记成「口是心非」——
而那是一条**高危痕迹**，会被单列出来给人看。所以 `claim` 必须写你**真的**
在代码里见过的东西，别写得漂亮。
另外必须回答 `control`：这次改动**动到了哪一层原有保护**。

**三条「参假」红线 —— 看到就必须单独出一条卡片记下来，不许替 AI 圆场：**

| 形态 | 长什么样 |
|---|---|
| 口是心非 | 它说「加了兜底」，实际改动是把兜底删了、或改成直接放过 |
| 包装凑数 | 把格式化、改名、加注释、调试残留包装成「决策点」交差 |
| 悄悄放水 | 删掉校验、吞掉异常、写死密钥、用 `--no-verify` 之类的命令硬提交 |

命中时 `decision` 要写成「AI 声称 X，实际改动是 Y」这种对照形式。

## 什么时候用 / 不用

用：用户说「记录一下这次改了什么决定」「复盘这版」「为答辩准备会被问到的问题」
「几天后我想再测一遍自己还记不记得」；或者刚完成一段有取舍的改动。

不用：用户只想要 diff 摘要、changelog、代码解释、或让我直接改代码。
**摘要不是决策记录** —— 遇到这类请求，先说明知迹产出的是问题不是解释，再决定要不要做。

## 工作流

### 第 0 步 · 确定仓库与改动区间

- 仓库：默认当前工作目录；用户给了路径就用用户的。
- 区间：默认 `HEAD~1..HEAD`。若用户说改动还没提交，用 `git diff HEAD`（工作区改动）。

### 第 1 步 · 拿到 diff

```bash
git -C <repo> diff --unified=3 <base>..<head>
```

按文件切开，逐文件分析。用 `git -C <repo> diff --numstat` 先看一眼规模。

### 第 2 步 · 找出 3–5 个决策点

- **单次上限 5 张。** 少于 2 张说明没找全；超过 5 张说明在凑数。
- 同一个文件最多出 3 张。
- 优先找这些信号：阈值/魔数、超时与重试、批量与分页、缓存、降级与兜底、并发与锁、
  数据切分、库与算法选择、边界条件的特判。

### 第 3 步 · 写卡片

**先问清楚用哪种写法**（它决定你用技术口吻还是大白话，见下方「卡片写法（两档）」）：

```bash
# 用户在界面上选过就写到 .env 里了；读不到就按 pro（专业模式）
grep -h COGNITRAIL_TONE <repo>/.env ~/.cognitrail/.env 2>/dev/null || echo "COGNITRAIL_TONE=pro"
```

用户没明说、也读不到时按 `pro`。**注意：这一档只改措辞，`file` / `claim` / `control`
这几个凭据字段在哪一档里都必须照原样给足** —— 小白模式不是把事实简化掉。

再确认项目主线（阶段清单）在不在 —— 卡片的 `stage` 必须从它里面选，
不先建它，几十张卡片各写一个阶段名，就拼不出项目地图：

```bash
python <engine>/cognitrail.py projectmap --repo <repo> --write-md
```

> 它落盘 `<repo>/docs/decisions/project-map.json`（项目目标 + 阶段清单 + 每阶段的典型卡点）。
> 已有的话它直接读、不覆盖；想重建加 `--refresh`。用户可以手改这个 json，那是权威版本。

写到 `<repo>/docs/decisions/<YYYY-MM-DD>-<两位序号>-<短标题>.md`。
字段名与小节标题**照抄下面的格式，一个字都不要改** —— 它对齐 AgDR 规范，
是「不自创格式」这句话的具体体现（`project` / `stage` / `problem` / `supersedes*`
是在 AgDR 之外补的四个字段，用来把卡片挂到项目主线、并记下它推翻了什么；
`tier` / `claim` / `control` / `signals` / `verdict` / `tier_why` 是审计字段）：

````markdown
---
id: D-<YYYYMMDD>-<NN>
project: <项目名>
stage: <从 project-map.json 的阶段清单里原样照抄一个，含编号，如 S2 打通模型通道>
problem: "<这一步遇到的问题 / 卡点：当时什么东西挡着，逼得必须做这个选择>"
tier: <key | normal | minor —— 见下方「怎么定档」>
file: <相对仓库根的路径，不要带 a/ 或 b/ 前缀>
lines: <起始行-结束行；只有一行就写单个数字>
decision: "<这次做了什么选择，一句话>"
why: "<为什么这么做。必须具体，禁止写'为了更好''更优雅'这类空话>"
claim: "<可被代码证实或证伪的事实断言。必须把关键的字面量原样写进来：数字、阈值、标识符、地址、参数名，例如『阈值由 0.5 改成 0.35』>"
control: "<这次改动依赖或动到了哪一层原有保护（校验 / 断言 / 边界判断 / 兜底 / 权限 / 唯一约束）：被保留、被加强，还是被绕过或删除；确实没涉及就整行删掉>"
alternatives: "<还考虑过什么、为什么没选>"
risk: "<这个选择的代价或风险>"
impact: "<影响范围：调用方 / 数据结构 / 对外接口 / 只影响本文件>"
tone: <pro | plain —— 写这张卡片时用的是哪种写法，见下方「卡片写法（两档）」。不确定就写 pro>
supersedes: "<这张卡片推翻了哪张更早的卡片（卡片文件名）；没有就整行删掉>"
supersedes_why: "<为什么推翻它：旧做法错在哪 / 为什么不再适用>"
status: active
created: <YYYY-MM-DD>
---

## 这次做了什么

<同 decision，展开成完整句子>

## 为什么

<同 why>

## 可核对的断言

<同 claim>

## 还考虑过什么

<同 alternatives>

## 代价与风险

<同 risk>

## 影响范围

<同 impact>

## 这次改动动到的保护

<同 control>

## 在项目中的位置

- 项目：<项目名>
- 阶段：<同 stage>
- 这一步的问题：<同 problem>

## 与已有决策的关系

- 取代了：`<同 supersedes>`
- 为什么推翻它：<同 supersedes_why>
````

**怎么定档**（`tier`）：

- `key` —— 动到了地基类文件（配置 / 凭据 / 数据结构与迁移 / 依赖清单 / 认证权限），
  或落在高风险行为面上（数据写入 / 并发与锁 / 金额与计费 / 权限 / 外部网络 / 外部副作用），
  或命中了上面那三条参假红线；
- `minor` —— 纯文档、纯注释、纯改名，没有改变对外行为；
- `normal` —— 其余。

> 宁可往高里定，不要往低里定。**动过凭据或默认值的，不许因为「只改了一行」标成 minor。**
> 引擎生成卡片时会自己按同一套规则再算一遍，且**只接受往上抬**。

**`claim` 是这一版最要紧的新字段。** 反例与正例：

- 反例（没法核对，等于没写）：`"提升了性能"`、`"更健壮了"`、`"符合最佳实践"`；
- 正例：`"阈值由 0.5 改成 0.35"`、`"超时从 30 秒改成 120 秒并去掉重试"`、
  `"删掉了『路径为空则 raise』的校验，改成直接 return"`。

写之前先看一眼同目录下已有的卡片（`ls docs/decisions/`）：如果这一轮的决定
**推翻了**某张旧卡片（同一件事、做法变了），必须填 `supersedes` 与 `supersedes_why`
—— 只记「现在用哪个」不记「为什么否掉旧的」，三个月后两版卡片互相打架，
读者不知道该信哪个。这两行没有可填的时候整行删掉，不要留空字段。

### 第 4 步 · 过闸门与过审计（不许跳过）

对每张卡片实测坐标：

```bash
python <engine>/cognitrail.py gate --repo <repo> --file <file> --lines <lines>
```

通过会打印 `OK` 并以 0 退出；不通过会打印 `DROP … —— 原因` 并以 1 退出。
**不通过的卡片，把那个 `.md` 文件删掉。**

闸门只管「这一行存不存在」，不管「卡片说的就是这一行」。所以过了闸门再走一遍审计：

```bash
python <engine>/cognitrail.py audit --repo <repo>
```

它按规则算出每张卡的重要性、核对结论与可疑痕迹，并给出**一句审计意见**
（无保留 / 带解释性说明 / 保留 / 未审计）。逐行输出的含义：

| 前缀 | 意思 |
|---|---|
| `OPINION` / `DETAIL` | 审计意见与理由。**结论看这一行，不要拿退出码当结论**（退出码恒为 0） |
| `COUNTS` | 卡片数 / 关键决策数 / 证据不充分数 / 存疑数 / 未取证数 |
| `KEY` | 关键决策：哪几条真正决定项目走向 |
| `SUSPECT` | 命中可疑痕迹的：拿掉校验 / 吞异常 / 写死凭据 / 绕过流程 / 断言与代码对不上 |
| `WEAK` | 证据不充分：断言里没有可核对的字面量 |

三条硬规矩：

- 审计结论是**脚本算的**，你不许自己改：卡片上 `signals` / `verdict` / `tier_why`
  三行以脚本输出为准（`tier` 你可以往上抬，不能往下压）。
- **「未审计」不等于「无保留」**：审计只会说「未审计」，那是「没查过」，
  不是「查过没问题」—— 汇报时不要把它说成通过。
- **你手写的卡片也会被核**：审计会拿你写的 `claim` 回仓库核一遍
  （断言里的数字 / 标识符在坐标附近找不找得到）。核出对不上，会记成
  「口是心非」并按关键决策处理；核**通过**时它**不会**写「无保留」——
  因为你手写的卡片没有 diff，「这次删掉了什么保护」看不见。
  想要完整核对，让引擎生成：`cognitrail run`。

### 第 5 步 · 出题 + 排期

给每张卡片出 3 个预设问题，再从 4 个角度各追问一层：

| 角度 | 问什么 |
|---|---|
| `[定位]` | 「你说这行是为了 X」—— X 对应代码里的哪一行？请给出 文件:行号。 |
| `[替代]` | 如果不用这个做法，你会怎么改？当时为什么没选它？ |
| `[代价]` | 这个做法有什么坏处？什么情况下它会出问题？ |
| `[迁移]` | 要在它旁边加一个新功能，你会从哪个文件开始改？ |

排进延迟探针（默认 3 天后到期）：

```bash
python <engine>/cognitrail.py probe --repo <repo> --schedule <卡片路径> --delay-days 3
```

### 第 6 步 · 把面板给用户看

```bash
python <engine>/cognitrail.py panel --repo <repo> --serve 8787
```

它会打印一行 `URL http://127.0.0.1:8787/dashboard.html`。
**把这个地址在 Codex 内置浏览器里打开** —— 这就是「打开 Codex 就能看见知迹」的样子。
如果用户不需要常驻面板，去掉 `--serve`，它只会把
`<repo>/docs/decisions/dashboard.html` 生成出来。

## 写法（两档：专家 / 小白）

用户可以在界面上选「专家模式 / 小白模式」（选择写在 `.env` 的 `COGNITRAIL_TONE` 里；
老写法「专业模式」也照旧认）。它换的是**给模型的写作口径**，不是换一套数据：

| | 专家模式 `pro` | 小白模式 `plain` |
|---|---|---|
| 读者 | 有经验的工程师 | 不一定懂编程的人（产品 / 运营 / 写作者） |
| 「做了什么」怎么说 | 在 `load_config()` 里把 timeout 的默认值由 30 改成 60 | 网络不好时不再反复等，直接给一个空结果 |
| 用词 | 行话要准（幂等 / 降级 / 事务边界），不解释基础概念 | 少用术语；非用不可就在括号里补一句人话 |
| 长度 | 一两句，信息密度优先 | 讲清「原来怎样、现在怎样、对我有什么影响」 |

它管的不只是卡片：界面里点「整理决策」「总结工作流」出来的文字，
以及窗口里「和 AI 对话」时那个 CLI 的答话口吻，都跟着这一档走。
报告类那几处用的是 `tone.block(kind="prose")` —— 不带卡片那套凭据字段要求，
但同样写明了「数字 / 路径 / 结论的把握程度一个字都不许动」。

**两档都一样、不许随写法变的部分：**

- `file` / `lines`（会话锚点卡片是 `quote`）—— 真实坐标，原样给；
- `claim` —— 必须含可核对的代码字面量（数字、阈值、标识符、参数名）；
- `control` —— 原有保护是被保留、加强，还是被绕过或删除；
- `stage` —— 从阶段清单里原样照抄；
- 审计那一节（`signals` / `verdict` / `tier_why`）照旧由脚本填，你不写。

卡片上要留 `tone:` 这一行写明用的是哪一档。少了它，后来的人看到
「页面更快但会少拿几条数据」这种句子，分不清那是**刻意写的白话**、
还是**你说不出准话** —— 这两种在纸面上长得一模一样。

## 出题的唯一原则

**问选择，不问事实。**

- 坏的：`VALIDATION_SPLIT 的值是多少？` —— 读代码就有，测不出任何理解。
- 好的：`把它从 0.2 改成 0.1 会怎样？` —— 必须真的想过才知道。

## 收尾必须汇报到的东西

1. 生成了几张卡片、写在哪个目录；
2. **丢了几张、每张为什么丢**（引用闸门打印的原因原文，不要自己转述）；
3. 排了几个复测题、哪天到期；
4. 一句提醒：面板不是重点，**几天后你还改不改得动**才是。

## 关于 API Key

在 Codex 里跑知迹**不需要任何 API Key** —— 分析 diff 的模型就是 Codex 自己。
插件里带的引擎只在独立命令行模式下才会去调模型（那时才需要 `.env` 里的 Key）。
所以不要因为「用户没配 Key」而拒绝使用这个技能。

## 也不一定要 Key：本机已装好的 CLI

用户本机要是装了 AI 命令行，可以直接借它来答问题（界面上是「和 AI 对话」按钮）：

```bash
python <engine>/cognitrail.py cli-chat --check                    # 只探测：装没装、什么版本
python <engine>/cognitrail.py cli-chat "这个项目的闸门怎么校验的"   # 直接问一句
```

自动认得这些（参数照着各自官方文档写的，别凭印象改）：

| key | 命令 | 提问怎么递 |
|---|---|---|
| `claude` | `claude` / `claude-code` | 标准输入（`-p`） |
| `codex` | `codex` | 参数（`exec <prompt>`） |
| `gemini` | `gemini` | 参数（`-p <prompt>`） |
| `qwen` | `qwen` / `qwen-code` | 参数（`-p <prompt>`） |
| `opencode` | `opencode` | 参数（`-p <prompt>`） |
| `cursor-agent` | `cursor-agent` | 参数（`-p <prompt>`） |
| `custom` | 用户自己填的 | 用户选 |

**找不到命令是常态，不是异常** —— 别人机器上的 CLI 可能装在自建目录、Scoop、
公司内网盘、绿色版里。这时候给出三条可操作的路，别只说一句「没找到」：

1. `.env` 写 `COGNITRAIL_CLI_PATHS=codex=C:\完整路径\codex.cmd`（手动指定，最优先）
2. `.env` 写 `COGNITRAIL_CLI_DIRS=C:\tools\bin;D:\npm`（额外搜索目录，`;` 分隔）
3. 界面上点「CLI 设置…」，每个命令一行填路径，旁边有「浏览…」和「测试」

这三样**每次调用都重新读**，改完不用重启。探测结果里会标明路径是
「手动指定」还是「自动找到」—— 排查时这个区别很关键。

另有三条注意：

- 这个通道**只问答**：不带 `--dangerously-skip-permissions` / `--force` / `--yolo`
  之类的开关，不会让另一个 AI 去改用户的文件。别自己加。
- 它有个已知坑：CLI 在未登录 / 没订阅时会把报错**当正常输出**吐出来（退出码还是 0）。
  引擎会认出来并判成错误 —— 这时候**不要说成「AI 回答了」**，
  照实说是 CLI 那边没连上，并给出原因。
- `opencode` 在非交互模式（`-p`）下会自行批准它自己的操作 —— 只适合问问题。

## 引擎位置（`<engine>` 是什么）

`<engine>` 是放引擎的目录，里面必须有 `cognitrail.py` 和 `src/`。它随安装形态而变，
按下面顺序找，**第一个存在的就是它**：

1. 本 SKILL.md 同级的 `scripts/`（个人技能形态：装到 `~/.codex/skills/cognitrail/` 时）
2. 插件根目录的 `scripts/`（插件形态：`<plugin>/scripts/`）

一个可靠的定位办法：在插件/技能目录里直接找这个文件名。

```bash
# 在技能目录下执行，取第一个命中
ls scripts/cognitrail.py 2>/dev/null \
  || ls ../../scripts/cognitrail.py 2>/dev/null \
  || find . -name cognitrail.py -not -path "*/src/*" | head -1
```

引擎结构：

- `cognitrail.py` —— 入口，子命令 `gate` / `panel` / `probe` / `cards`
- `src/` —— 引擎本体（从项目 `src/` 同步而来，**不要在这里改**）
